# SlideHub · PPT 模块化管理与版本控制

> 方案 v3 · 已迁入 Deck-Organizer 仓库并落地为可用工具，见 `README.md`

---

## 1. 定位

**按页搭建 + 版本控制 + 云端同步。**

上传现有 deck → 自动拆成「页」入库 → 按板块/案例筛选 → 勾选拼成一份 → 下载给客户。
页改过之后传回来，作为该模块的**新版本**存下来，下次可选。云端唯一事实来源，多人共用。

### 明确不做

写下来是为了防止范围漂移：

| 不做 | 为什么 |
|---|---|
| 在线编辑 PPT（改字、调版式、换图） | 编辑永远在 PowerPoint 里做，那是它最擅长的事 |
| 统一/重挂母版，自动改版式 | 页面原样进、原样出。见第 6 节：改母版就是在改 PPT，且必然引入视觉 bug |
| 变量替换、目录重排、页码重编 | 同上，属于编辑行为 |
| AI 自动写页、自动生成内容 | 内容是人的事 |

系统只负责三件事：**存哪些页、页有哪些版本、把选中的页拼起来。**

## 2. 三个核心对象

```
Module  模块（逻辑页）
  ├─ 一个语义单元，如「公司简介-一句话定位」
  ├─ 标签：板块 / 行业 / 客户 / 语言 / 密级
  └─ default_version → 主版本（拼装时默认用它）
       │
       └─ Version  版本（物理页）
            ├─ 自包含的单页 pptx + 缩略图 + 文本 + 指纹
            ├─ label：人写的名字，如「2025Q3 数据版」「英文版」
            ├─ parent_version：从哪个版本改来的
            └─ status：草稿 / 已批准 / 已弃用

Recipe  配方（一份方案）
  └─ 有序的引用列表，每条要么跟随模块主版本，要么锁定某个版本
```

`SourceDeck`（原始上传件）和 `Export`（每次导出记录）是附属，用于回溯。

## 3. 版本控制模型

### 3.1 版本树

同一模块下的版本是**并列可选**的，不是单纯的时间线：

```
Module「案例 · 某新能源车企 · 传播效果」
├── v1  2024 原始版                        已弃用
├── v2  2025Q1 数据更新    ← parent: v1    ★ 主版本
│   └── v4  英文版         ← parent: v2    已批准
└── v3  极简一页版         ← parent: v1    已批准
```

- `parent_version` 记录血缘，UI 上就是一棵树 + 缩略图并排对比
- `default_version` 是主版本指针，拼装时默认选中，可手动切
- **不要 git 的 merge 心智**：PPT 页没法自动合并，人也不需要。需要的只是「并排看，选一个」

### 3.2 引用模式：跟随 vs 锁定

这是「同步更新」的基础。配方里的每一页有两种引用方式：

| 模式 | 含义 | 用在哪 |
|---|---|---|
| **跟随**（默认） | 指向模块，导出时解析为**当前主版本** | 公司介绍、服务说明这类会持续更新的页 |
| **锁定** | 指向一个具体版本，永不变 | 已经报过价、已经发给客户存档的方案 |

## 4. 同步更新机制

先说清楚一个物理限制：**下载下来的 .pptx 是死文件，不会自己更新。**
所以「同步」只能是「云端发现差异 → 提示 → 一键重新生成」。

### 4.1 检测

每次导出记录实际用到的 `(module_id, version_id)` 集合。
当某个模块的主版本发生变化时，反向扫描所有配方与导出记录：

```
某模块主版本 v2 → v5
        │
        ├─ 配方《某客户年度提案》以「跟随」方式引用该模块
        │     → 标记「有更新可用」
        │
        └─ 配方《XX 报价方案》锁定在 v2
              → 不动，但在详情页提示「上游已更新，是否解锁」
```

### 4.2 呈现

「我的方案」列表上直接显示状态：

```
某客户年度提案        42 页    ● 4 页有更新      [重新生成]
XX 快消行业提案       28 页      已是最新
YY 报价方案           15 页    ⚑ 2 页已锁定（上游有更新）
```

点「重新生成」→ 产出新的导出件，**旧导出件保留**，历史可追可对比。

### 4.3 通知

飞书机器人推给配方 owner：「你的《某客户年度提案》有 4 页已更新，是否重新生成」。

### 4.4 并发

两个人同时改同一页 → 两个都成为新版本，并列挂在模块下，由模块 owner 决定谁是主版本。
**不做自动合并，不做锁**。这符合 PPT 的实际协作方式。

## 5. 四条工作流

### 5.1 入库

上传 deck → 拆成单页 → 渲染缩略图 → 算指纹 → **自动聚类去重** → 打标签 → 入库。

去重是入库的核心价值：同一页在几十份 deck 里的重复副本会被收敛成一个模块下的若干版本。
产出的报告本身就是说服材料：「34 份 deck、2100 页 → 约 480 个独立模块」。

标签用**分面**而不是树（一页天然属于多个维度）：
`板块` `子板块` `行业` `客户` `语言` `页型` `密级` `数据时点` `状态`

> **密级是最重要的一个字段**。案例页里有客户名、效果数据、有时还有报价。
> 导出前必须强制拦截「内部限用」页，不能只靠人记得。

**打标由人工完成。** 自动打标试过并否掉了 —— 词表能抽出的是一页「提到了什么」，
不是这一页「是什么」，同一批词会同时命中真实案例、能力说明页和章节分隔页。
详见 `README.md`。导入时不打标签；标签目录预置草稿词表，全部可增删改。

### 5.2 检索

分面筛选 + 关键词，缩略图网格。卡片显示：板块、行业、版本数、最近使用、密级。

### 5.3 拼装下载

左边筛页，右边拖拽排序，存为配方 → 导出 PPTX（+PDF）。
每页埋入不可见来源标记，导出记录完整配方快照。

### 5.4 回传沉淀

上传改过的 deck → 逐页识别来源 → 分类 → 人工确认：

| 情况 | 动作 |
|---|---|
| 没变 | 忽略（支持一键忽略所有未变更页） |
| 改过 | **存为该模块的新版本**，可选是否设为主版本 |
| 全新的页 | 作为新模块入库 |
| 导出时有、回传时没了 | 记为「被删」信号 |

## 6. P0 技术验证结果（已完成）

代码在 `tools/slidehub/`，一条命令可复现：`python3 -m slidehub spike`。

### 6.1 结论

| 验证项 | 结果 |
|---|---|
| 跨 deck 抽页拼装保真度 | **10/10 页与源渲染完全一致**（感知哈希距离 0，颜色差 0.00） |
| 回传来源识别 | **10/10 页标记可恢复**，deck 级 manifest 完好 |
| 回传变更分类 | 模拟改字/删页/移动/剥标记/加新页，**5 类全部正确识别** |
| 是否需要商业库 | **不需要**。python-pptx + LibreOffice 足够 |

测试样本是三份**主题色和字体各不相同**的 deck（青/橙/紫），覆盖占位符、图片、表格、原生图表、分组形状、渐变背景 —— 即跨 deck 拼装最容易崩的那些元素。

### 6.2 保真度靠什么做到

**不改页**。每页连同它自己的版式、母版、主题一起搬过去，仍然挂在原版式上。
产物里每份源 deck 带一套母版，这是代价，也是对的代价。

对照组做过另一条路（把页重挂到统一母版，需要解析主题色、bake 继承的文字样式、注入图表配色）：
实测 **mean 7.80 / worst 19，3 页超阈值**；补上文字样式 bake 后降到 mean 1.20，
但**图表的柱子从橙色变成了青色** —— 因为图表颜色根本不在 slide 里，
而在独立的 chart part 中，靠目标主题推导。这条路已废弃，因为它本质上是在改 PPT。

### 6.3 顺带发现的两个坑（已修，会带进正式实现）

1. **python-pptx 的 `add_slide` 会生成重名 part**
   它用 `len(sldIdLst) + 1` 推导路径（文档字符串却写着 "next available"）。
   删一页再加一页 → `slide10.xml` 撞名 → 文件损坏。
   而「删了再加」正是本产品最高频的操作。已用 `pptx_compat.add_slide` 绕开。

2. **母版会按页重复克隆**
   每页是独立打开的文件，同一份源 deck 的母版在拼装时被克隆了 N 次。
   10 页产出 11 套母版，60 页就会产出 60 套 —— PowerPoint 的母版视图一团糟，体积白涨一倍。
   改成对 part 的**整个可达子图**做哈希去重后：3 份源 deck → 3 套母版，体积从 263KB 降到 116KB。
   （只按 part 自身字节去重是不够的：三份样本 deck 的 `slideMaster1.xml` 完全相同，
   只有挂在下面的 theme 不同，按字节去重会把不同品牌色的母版合并掉。这个错误正是被下面的颜色检测抓住的。）

3. **灰度感知哈希看不见颜色变化**
   dhash 对上述「橙柱变青柱」给出的距离只有 2，低于阈值，**判定为通过**。
   保真度检测必须同时带一个颜色维度的信号。已加。

### 6.4 保真度回归检测

导出后渲染成图，逐页与入库时的缩略图比对（结构 + 颜色两个信号），超阈值标黄。

> 这里有个关键点：比对的是「同一渲染器渲染的源页」对「同一渲染器渲染的成品页」，
> 渲染器本身的不准确在两边**相互抵消**，所以即便渲染引擎对 PPTX 还原不完美，这个检测依然可靠。

## 7. 技术架构

| 层 | 选择 | 理由 |
|---|---|---|
| 前端 | Next.js + TypeScript + Tailwind + dnd-kit | 拖拽拼装 |
| 后端 | Python + FastAPI | PPTX 处理全在 Python 生态，不拆两种语言 |
| 异步 | Redis + arq | 入库慢，必须异步 + 进度条 |
| 数据库 | PostgreSQL | JSONB 存分面标签，一个库够用 |
| 对象存储 | S3 兼容（OSS / COS / MinIO） | 原始 deck、单页 pptx、缩略图、导出件 |
| 渲染 | LibreOffice headless + unoserver | unoserver 让进程常驻，比冷启动快 5–10 倍 |
| 登录 | 飞书 OAuth | 免维护账号体系，权限对齐组织架构 |
| 部署 | Docker Compose · 单台 4C16G | 10–50 人规模足够 |

**渲染容器必须预装公司在用的中文字体**，否则缩略图全是豆腐块。

### 飞书怎么用

独立 Web 应用为主体，飞书做外围四件事：
**① OAuth 登录 ② 打包成飞书网页应用（工作台直接打开，推广门槛低） ③ 机器人通知更新/审批 ④ 可选：模块索引同步到多维表格做只读视图**

不要试图做进多维表格 —— Base 处理不了 PPTX 的拆、渲、拼。
